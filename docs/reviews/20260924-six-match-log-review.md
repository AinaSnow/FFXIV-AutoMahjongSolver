`automated=false` 只能证明回调不在本插件自动输入作用域内，不能单凭此字段认定是用户手动点击。修复应针对该弹窗的取消路径、杠类型识别和重复无效派发计数，不能只把返回 Ok 当作执行成功。

### 2. Mortal 立直响应的序号过滤疑点

五次超时中三次是对手立直后等待鸣牌回应：20:27:46.903、21:07:56.116、21:09:02.400。三个时刻最后发出的 MJAI 均为 `reach_accepted`，队列为 0，无抓包丢弃。

代码路径与现象吻合：生产解码器将一次立直弃牌转换为 `reach → dahai → reach_accepted`；当前 MortalProcessClient 只派发序号等于最新发送序号的结果。libriichi 的 Bot 对每条事件调用普通 update，公告事件会清除可行动候选。因此针对 dahai 的有效建议可能因后续 reach_accepted 已发送而被过滤，公告自身又不产生补充建议。

这是有具体事件与代码依据的根因假设，尚未通过本轮真实 runner 回放或进程传输回归确认。应按同一行动窗口及实际使建议失效的事件管理响应，继续保留跨进程、跨手局和动作合法性校验，不能直接取消所有过期保护。

其余两次：21:08:01.392 自身出牌超时，紧跟前一次重启；21:57:11.968 鸣牌超时，最后消息为其他玩家摸牌，需检查 UI 弹窗与事件先后。已保留窗口，不能都归因于模型计算慢。
