# Mortal 半庄权重对照入口与首次验证（2026-09-25）

已实现独立 checkpoint 对照，不再局限于内置策略与 Mortal 的比较。在线权重、Mortal 配置和自动排队模式均未修改；没有训练新权重，也没有执行 1,000 组正式验收。

## 本轮实现

- 候选、基线、固定三名对手各自独立加载模型；运行器无参数启动保持现有配置，显式离线覆盖不会改写它。每个引擎保留自己的模型哈希，避免后加载的模型覆盖前者的身份。
- 相同种子分别执行候选/基线四座轮换。每组交替执行顺序，固定对手模型；关闭探索、混合精度与随机 latent。模型只获取对应玩家可见信息。
- 核验牌谱起止、种子、四座完整性、座位上的模型名称及引擎返回名次。每手双响只记一次放铳，自摸不会算作放铳。
- 同模型控制实验逐座比较完整游戏事件哈希和成绩；不一致则失败。中途异常标记 failed，只保留已经完整验证的配对组，不产生完成报告。
- 报告包含名次分布、平均名次、前二率、每手和牌/放铳率、牌桌得失分和按种子组计算的区间。标准半庄结果不会自动晋级为 FF14 默认模型。

## 实测结果与限制

同模型控制实验使用开发种子 1000200，完成 8 场，四座前后牌局与成绩完全一致，名次差为 0。这验证了该次运行的配对和统计路径，不是对所有硬件的逐动作确定性保证。

候选使用本机已有 `mortal_298k.pth`，基线及三名对手均为当前 `model_v4_20240308_best_min.pth`。候选格式兼容，保留的训练配置使用名次奖励 [6,4,2,0]；来源和授权没有完成追溯，因此只是离线实验候选。开发种子为 1000300、1000301，各执行候选/基线四座，共 16 场。

## 规则边界

- Pinned OneVsThree runs standard eight-hand hanchan, not Doman quick four-hand matches
- libriichi extends beyond scheduled rounds below 30000; Doman has no extension
- libriichi final-dealer finish requires 30000 and first place; Doman does not require 30000
- Doman single-yakuman values, four-yakuman cap, multiple wins, abortive draws, nagashi and pao need engine parity tests
- Doman 80/120-minute limits and game input latency are not simulated


**仅两个独立种子组，不能据此宣布候选更强或提高了真实胜率。** 小样本 bootstrap 区间只是在这两个观测组上的重采样，其表面宽度不能代表对未来牌局的可靠把握。正式统计门槛未通过，因为这不是独立的 1,000 组验收集。

基线对手恰好是同一份权重的副本，关闭探索后相同牌山的四次轮换可能产生相同牌局；轮换只是从四个座位评价它，因此这一设置下基线平均名次 2.5、前二率 50% 是正常的。它不是用户 FF14 的真实成绩，也不说明当前模型只能打到五五开。候选的牌桌平均得失分与 Rating 收益没有直接换算关系。

## 验证与复现

- Python 全部 48 项测试通过，包括旧 runner 行为、多个模型身份隔离、座位对应、多人和牌统计、失败归档与固定对手配对。
- Release 插件构建成功，0 警告、0 错误；本轮无 C# 逻辑改动，不重复声称运行了 .NET 全套测试。
- 实测控制对照 8 场、不同权重对照 16 场均正常结束；原始压缩牌谱、manifest 与结果保留在 artifacts/evaluation/models-control-20260925 和 artifacts/evaluation/models-298k-20260925，没有提交原始牌谱或模型。
- 已核对当前权重与 Mortal config 文件校验值未变。构建产物位于原 dev 输出目录；本轮不需要为了离线评测重启游戏或强制热重载。
