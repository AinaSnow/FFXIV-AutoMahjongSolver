# C1：实机结算标签与服务端动作核对（7.58，44 场）

数据：2026-11-14/15 的 44 场托管归档（其中 41 场有 `packets.ndjson`）和 42 份原始录包，客户端 `2026.11.03.0000.0000`，`Emj`，profile [20261103-international-candidate.json](../../data/protocols/20261103-international-candidate.json)（`verified: false`，本轮不改）。原始数据只读，没有复制进仓库；回归 fixture 只保留解码器读取的字段。

## 结论

1. **结算报文已解开，所有手局都能给出标签。** 639 = 自摸、640 = 荣和（最多两个和牌者块）、643 = 流局（`@0` 区分荒牌流局与途中流局）。41 场归档的 213 手、42 份录包的 217 手全部得到非 unknown 的结果；每个字段都和独立证据核对过，没有不一致。
2. **放铳者不是报文字段。** 和牌者块里 63 个字都能对上含义，没有放铳者。放铳者取最后一张舍牌（抢杠时取加杠）的玩家，只有当分数增减和它完全吻合时才采用，否则整手标为 unknown。
3. **双响已能处理。** 640 的第二个块在双响时带第二位和牌者，点数是累计的。旧复盘看到的“只有第一位和牌者”是因为只读了第一个块。本批 2 手双响都已核对；本场棒/供托在双响时怎么分配还没有样本，见“未证明”。
4. **自家动作的服务端核对：44 场中没有一次服务端与派发不一致。** 有报文的 41 场里，舍牌 2305/2305、立直 43/43、立直宣言牌 43/43、荣和 52/52、自摸 15/15、碰 57/57、吃 52/52（含 10 次两步选型）、加杠 1/1 全部由服务端确认；暗杠 2/3 确认，剩下 1 次就是 A3 复核里那次无效的立直暗杠点击（`server-no-effect`）。没有报文的 3 场（11-14 无协议）标为 `no-server-evidence`。
5. **Pass 无法被服务端“确认”。** 服务端从不回执过牌，所以单独标为 `server-window-closed`（窗口在我方没有鸣牌/和牌的情况下关闭），不算 `server-confirmed`。572 次属于这一类，152 次点在服务端根本没有开放窗口的残留行上（`server-no-window`）。
6. **训练资格不变：0 条 `training_eligible`。** 各项完整性检查都已实现为独立的标志；只剩协议门槛时，44 场中有 41 场、3142/3704 条样本会合格。另设了一个更弱的“对手统计”层级，需要用户决定是否采用（见第五节）。

## 一、结算报文布局（7.58）

偏移是 little-endian int32 的字序号（字节偏移 = 4 × 字序号）。座位是服务端座位，每手以庄家为 0；转成相对座位用开局包 `@24` 的自家座位。点数单位是百点。

**和牌者块（63 字）**

| 字 | 含义 | 核对方式 |
|---|---|---|
| w0 | 和了牌种（`+0x100` 为赤五） | 荣和：等于最后一张舍牌；自家自摸：等于摸到的牌 |
| w1 | 公开的闭手张数（1/4/7/10/13） | 与副露数一致（未单独计数） |
| w2 | 满贯档位（0 无、1 满贯、2 跳满、3 倍满…） | 由番符推出的档位 194/194 一致 |
| w3 | 番数 \| 获得的供托根数 << 8 \| 本场 << 16 | 番数 = 役值之和 194/194；本场 = 开局本场 189/189；供托进入点数核算 |
| w4 | 和牌者座位，4 = 空块 | 自摸 = 最后摸牌者 58/58；荣和 ≠ 放铳者 |
| w5 | 打点 | 由番、符、是否庄家按标准点数表算出 194/194 |
| w6 / w7 | 自摸时庄家 / 每个闲家的支付（负数，荣和为 0） | 60/60 |
| w8 | 符 | 参与打点核算 |
| w9–w12 | 本块结算后的四家点数 | 与下一局开局、UI 分数一致 |
| w13–w25 | 公开的闭手牌 | 未用于标签（fixture 中清零） |
| w26–w41 / w42–w57 | 役种 ID / 役值（宝牌项打包 `[合计, 里宝, 赤宝]`） | 与 `audit_kan_dora.py` 一致；未用于标签 |
| w58–w62 | 里宝牌指示牌 | 未用于标签 |

- **639**（256 字节）= 一个块 + 一个恒为 0 的字：自摸。58 次 w6/w7 都非零。
- **640**（504 字节）= 两个块：荣和。第二个块平时为空（w4 = 4，牌全为 0xFF）；双响时是第二位和牌者，w9–w12 是两人都结算后的累计点数。
- **643**（264 字节）：w0 = 0 荒牌流局（23 次）/ 1 途中流局（1 次）；w1 恒为 255；之后每家 16 字 `[结算后点数, 公开张数, 牌…]`，公开张数 > 0 即听牌。

**点数核算规则**（全部 213 手成立）：荣和时和牌者得 `打点 + 300×本场 + 1000×供托`，放铳者付 `打点 + 300×本场`；自摸时庄家付 `w6 + 100×本场`，闲家付 `w7 + 100×本场`；本手宣告立直的其他玩家各 −1000。和牌者自己的立直棒算作退回，不计入 w3 的供托数；被荣和的立直宣言牌不形成供托（双响那手正是这种情况）。荒牌流局按听牌人数分 3000 点。

## 三、实现：为什么是“C# 旁路 + Python 镜像”

- 现有 44 场归档已经有报文，回溯打标签必须离线解码，所以 [`tools/live_hand_labels.py`](../../tools/live_hand_labels.py) 是必需的；它供 `training_dataset.py` 和 `opponent_stats.py` 使用。
- 实机核对和牌（“结算里我方是和牌者”）必须在插件里读结算包，所以解码器也要读。读出的结果放在 [`MahjongPacketMjaiDecoder.LastHandResult`](../../Mahjong.Plugin.Game/Mjai/MahjongPacketMjaiDecoder.cs)，解析在 [`ServerHandResult.cs`](../../Mahjong.Plugin.Game/Mjai/ServerHandResult.cs)。**`MjaiEndKyoku` 和发给 Mortal 的内容不变**；读不通的结算包只得到 `unknown`，从不抛异常，不会隔离手局（回归测试对五种篡改都验证了这一点）。
- 两边的实现相互独立，用同一个脱敏 fixture 检查，并在 217 手录包上逐手比较，结果完全一致。`Mahjong.PacketReplay` 的每手输出新增 `result`，`audit_live_archives.py` 会把它写进报告。

## 四、服务端动作核对

### 判定规则

每个派发成功的动作，按时间找它之后决定该决策点的第一个服务端事件：

| 状态 | 含义 |
|---|---|
| `server-confirmed` | 服务端把这个动作归于我方：同牌种且同赤五身份的 `dahai`（派发时未记录赤五身份则只比牌种，并写明原因）、`reach`、同类型的鸣牌/杠、点名我方为和牌者且和牌方式相同的结算 |
| `server-action-mismatch` | 该决策点上我方在服务端做了别的动作 |
| `server-window-closed` | 仅 Pass：报价窗口（他家舍牌/加杠，或自家摸牌后的宣告）在我方没有鸣牌、和牌或宣告的情况下关闭。服务端从不回执过牌，他家优先鸣牌或计时到也是同样的表现，所以这是“一致”，不是“确认” |
| `server-no-window` | 点击时服务端没有开放任何报价（残留行、过期提示），点击本身不可能是服务端动作 |
| `server-no-effect` | 鸣牌/杠/和牌点击后，决策点关闭了但该动作没有发生 |
| `server-superseded` | 同一决策点由我方另一次派发决定（重试、残留行上的 Pass） |
| `server-unconfirmed` | 有报文但没有决定性事件（例如手局先结束、结算 unknown） |

A3 复核里的几种情况都按上表处理：残留行上的 Pass 是 `server-no-window` 或 `server-superseded`；被取代的重复点击是 `server-superseded`；无效的杠点击是 `server-no-effect`。吃的“打开选型列表 + 选型”两步、立直的宣言 + 宣言牌、和牌的两次确认点击都算同一动作的步骤，各自保留状态。

`server-action-mismatch`、`server-superseded` 和 `server-unconfirmed` 在 44 场中都是 0。

- **唯一的 `no-effect`**：`match-20261115-113816Z` 第 1 手的立直暗杠（A3 #1），服务端紧接着是自家摸切中，与 A3 复核一致，属于真实执行问题，不是标签错误。
- **152 次 `no-window` Pass**：149 次是摸牌后对过期提示的 `[8]` 取消，2 次在他家吃之后（A3 #2 的两次超时兜底），1 次在自家舍牌之后（A3 #3）。

### 实机日志

游戏日志 schema 升为 9，只新增两种记录，原有记录不变：

- `server-outcome`：`action_id`、`label`、`status`、`reason`、`server`。覆盖舍牌、立直、和牌、Pass，以及无效的鸣牌/杠点击（`server-no-effect`）。已确认或不一致的鸣牌/杠仍由原 `ServerCallOutcomeTracker` 写 `action-outcome`，两者不重复。
- `server-hand-result`：解码器的结算标签（相对座位）。

UI 的 `action-outcome`（`state-changed` 等）不受影响，派发、重试、计时都没有改动。

## 七、已证明与未证明

已证明（本批数据内）：

- 639/640/643 的上述字段含义，以及荣和、自摸、荒牌流局的点数核算；放铳者由最后舍牌推出且与点数一致；双响的第二个块。
- 41 场有报文的归档里，我方每个派发的舍牌、立直、和牌、鸣牌在服务端的去向。

未证明，遇到时会退化为 `unknown`，不会被猜测：

- **双响时本场和供托的分配**：2 个样本本场都是 0，桌上也没有供托。两个块各自带本场/供托字段，如果服务端的实际分配与块内字段不一致，点数核算会失败。
- **三家和**：640 只有两个块，从未出现；可能以途中流局形式出现，此时公开手牌的不是最后摸牌者，会标为 unknown。
- **流局满贯**、**四家立直**、**四风连打**、**四杠散了**：都没有样本；流局满贯会让流局点数核算失败。
- **途中流局的种类**：不是报文字段。
- **抢杠**：没有样本；放铳者会取加杠者，同样要过点数核算。
- **w1 = 255、w2 的更高档位（役满）、w26 起的役种 ID**：只用于一致性检查或没有用到。
- 所有 profile 仍为 `verified: false`，`DomanMortalTrialGuard` 的准入不变，`0x400/0x240/0x213` 仍被拒绝。
